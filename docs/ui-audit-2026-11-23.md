# UI/UX audit: Party Hostess Scheduler

Date: 2026-11-23
Scope: `web/` (Next.js 15.5.29 app). Read-only. No code or data was changed.
Live: https://parties.birdbowl.com (sign-in and sign-out verified; admin page verified).

## 1. Screens inventory

| Route | Who | Purpose |
|---|---|---|
| /login | Signed out | Email or phone one-time code |
| /pending | Signed in, not approved | Waiting screen; name form |
| /app | Staff | Own time slots for next two weeks; party details after morning reveal |
| /admin/users | Admin | Approve requests, set status, role, host tier, daily cap |
| /admin/settings | Admin | Scheduling settings |
| /manager/schedule | Manager | Week view, engine preview, reassign, save assignments, fairness table |
| /sales/parties | Sales | Week list, add, edit, cancel parties |

Shared: `layout.tsx` (one `<main>` wrapper), `globals.css` (310 lines, design tokens), `admin/nav.tsx`.

## 2. Findings

### Responsiveness (highest priority)
- **Only one media query exists**: a dark-mode query (`globals.css:20`). There are no breakpoints for tablet, laptop or ultrawide.
- The page wrapper centers a `max-width: 400px` card. The manager and sales pages add `.wide` (960px). Neither changes layout at small widths.
- The manager fairness table is inside `.table-wrap` with `overflow-x: auto`, which prevents page overflow but makes the table hard to use on a phone.
- Ultrawide: the content sits in the center at fixed widths, with no use of extra space. Not checked visually (see Gaps).

### Design system
- Tokens exist for color, spacing and radius (`:root`), and dark mode is defined in three places (`prefers-color-scheme` and `data-theme`). The token set is small: no type scale, no shadow or motion tokens, no elevation.
- Buttons are all one style, with a `.secondary` variant. No danger, icon, or loading variants. Disabled state exists (opacity 0.6).
- Inline styles: none. Good for maintenance.
- Dark mode: the `data-theme` override and the media query duplicate the same values. Maintenance risk if one changes.

### Accessibility (WCAG 2.2 AA)
- Good: visible focus ring on inputs, buttons and links (`:focus-visible`), 44px minimum targets, `lang="en"`, labels tied to inputs, `role="alert"` on errors, `aria-current` on the admin tabs, `scope="col"` on table headers.
- Gaps to check:
  - Contrast of `--color-muted` (#5b6573 on #f7f8fa) and dark muted (#9aa4b2 on #171b21). Needs a measured check.
  - Login: the "If that email can sign in..." message is `role="status"`, but the code input has no visible instructions for paste behavior. Minor.
  - Sign out in the admin nav sits between tab links. It works, but a screen reader hears it as navigation.
  - Table on the manager page: check that the caption or heading names the table.
- No skip link. The layout has only one `<main>`; with a small nav this is acceptable but should be added.

### UX / flow
- Sign-in: two channels (email, phone). Phone is not configured. Showing the Phone tab with no working path is a dead end. Consider hiding it until phone sign-in is live.
- Sales: a moved assigned party shows a clear message (fixed earlier). Good.
- Admin: the user row shows the email twice when no name is set. Cosmetic.
- Admin: the Sign out button placement (between tabs) is inconsistent with other screens. The staff page puts it at the bottom.
- Navigation is per role with no shared shell. Staff, managers and sales each have their own page layout and no shared header. This is the biggest structural gap for a redesign.

### Security (front end)
- No `dangerouslySetInnerHTML`. No service-role or secret strings in `src/`.
- Server-side role guards in each page (`requireAdmin`, `requireManager`, `requireSalesAccess`) plus RLS in the database. Front-end checks are only UX.
- Sign-out is a POST form (protects against link-based sign-out).
- Robots noindex set on all pages.
- Dependencies: `next` is 15.5.29. Earlier audit: `postcss` and `sharp` high via transitive dependencies, `next` moderate, Supabase packages low. Upgrading Next to 16 is a separate decision (not made).

### Performance
- Pages are `force-dynamic`, which is correct for session data. No client-side data fetching except the login form.
- Fonts: system stack only. No web-font download. Good.
- Not measured (no Lighthouse run yet).

## 3. Gaps in this audit

- **Screenshots at phone, laptop and ultrawide widths were not captured.** Chrome did not change the viewport when resized. Only the signed-out sign-in page was checked, at one width.
- **Signed-in screens were not reviewed visually** (staff, manager, sales, admin pending/settings). Each needs a sign-in with that role. I can't receive email codes; you would need to sign in on each and share screenshots, or give access another way.
- **Contrast was not measured.**
- **Lighthouse / performance not run.**
- **Manager and sales flows not exercised on production.**

## 4. Open context questions (needed before design)

From the redesign workflow (CLAUDE.md section 16):
1. Main users and their key tasks. (Who uses the staff page on a phone? Who uses the manager week view on a desktop?)
2. What to keep: logo, brand colors, navigation structure.
3. Reference screens or sites you like.
4. Biggest pain points today.
5. Dark mode needed, or light only?

### Answers received (2026-11-23)
1. **Users:** staff use phones (mobile is important); managers and sales use desktops. Design staff screens mobile-first; manager and sales screens for laptop, working on tablet.
2. **Keep:** existing logo, brand colors (blue accent), and current navigation structure. Blue stays, but its visibility in dark mode must be fixed (brighten the dark-mode accent, keep the hue; measure contrast in both themes).
3. **References:** Linear, Stripe Dashboard, Notion.
4. **Biggest pain point:** mobile use for staff (no phone layout today).
5. **Dark mode:** light and dark, both designed and contrast-checked.
